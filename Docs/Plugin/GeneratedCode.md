# Generated code

An annotated tour of the file `ZerkPlugin` writes. Every listing below is real
codegen output — the fixture on the left was run through `ZerkCodegen` and the
result pasted verbatim.

## Where the file is

One file per target: `Zerk.generated.swift`, inside the plugin's
work directory in the build directory. It is declared as the codegen command's
only output, so the build system reruns codegen exactly when a source file or
`ZerkSettings.json` changes.

Under SwiftPM the path is
`.build/plugins/outputs/<package>/<target>/destination/ZerkPlugin/Zerk.generated.swift`.
Under Xcode the same file lands in the project's DerivedData. In both cases the
reliable way to find it is to search for its name:

```bash
find . ~/Library/Developer/Xcode/DerivedData -name Zerk.generated.swift
```

**Never edit it.** It is rewritten from scratch on every build that touches a
source file, and it is not in your repository. The file exists to be read — when
a member is not where you expected it, when an `inject()` grew a parameter you
did not ask for, or when a diagnostic points at a shape you want to see — and to
be regenerated, never to be changed.

Emission is deterministic: keys, members, imports and interjection points are all
sorted, so the file is byte-identical between builds of unchanged sources.

Alongside it the plugin writes [`Zerk.graph.json`](GraphArtifact.md) — the same
resolution, as data rather than as Swift. Use it when the question is about the
*graph* (which provider won a key, what depends on what, what is kept alive)
rather than about the code.

## The header

```swift
import Zerk

@Injectable
struct Stamp {
    @InjectableProviding
    init(at: Date) {}
}
```

```swift
// Generated by Zerk
// Do not change by hand.

import Zerk
import Foundation
```

The generated file imports `Zerk` and nothing else by default — the plugin reads
syntax and cannot tell which module a name came from, so it cannot infer that
`Date` needs `Foundation`. Everything after `import Zerk` was copied from the imports of the files Zerk
read, sorted; `Zerk` stays first because it is the one import that is never
optional.

## The re-declared `macro Injected` overloads

Every generated file re-declares `@Injected` and `@InjectedDynamically` into the
module it generates into:

```swift
@attached(peer, names: prefixed(_$zerk_injection_))
macro Injected() = #externalMacro(module: "ZerkMacros", type: "InjectedMacro")

@attached(peer, names: prefixed(_$zerk_injection_))
macro Injected<T>() = #externalMacro(module: "ZerkMacros", type: "InjectedMacro")

@attached(peer, names: prefixed(_$zerk_injection_))
macro Injected<T>(_ keyPath: KeyPath<Zerk<T>.Type, T>) = #externalMacro(module: "ZerkMacros", type: "InjectedMacro")

@attached(accessor)
macro InjectedDynamically() = #externalMacro(module: "ZerkMacros", type: "InjectedDynamicallyMacro")

@attached(accessor)
macro InjectedDynamically<T>() = #externalMacro(module: "ZerkMacros", type: "InjectedDynamicallyMacro")

@attached(accessor)
macro InjectedDynamically<T>(_ keyPath: KeyPath<Zerk<T>.Type, T>) = #externalMacro(module: "ZerkMacros", type: "InjectedDynamicallyMacro")
```

These mirror the library's own declarations, and being module-local they shadow
them wherever the plugin runs. The roles never cross: every `Injected` overload
is a peer, every `InjectedDynamically` one an accessor. Mixing them under a single
name crashes SILGen, which is the whole reason there are two names. That is the point: a macro attribute can
only carry arguments some declaration accepts, and the library cannot declare
every argument list a module's `inject()` methods might take. So the plugin adds
**one overload per distinct `inject()` signature** in the module. Given

```swift
@Injectable
struct Report {
    let store: any Storing
    let title: String
    init(store: any Storing, title: String) { ... }
}
```

whose `inject()` bubbles `title` up to the caller, the file also carries:

```swift
@attached(peer, names: prefixed(_$zerk_injection_))
macro Injected(title: String) = #externalMacro(module: "ZerkMacros", type: "InjectedMacro")
```

which is what makes `@Injected(title: "Q4") var report: Report` legal. Signatures
are deduplicated: two keys whose `inject()` takes `(title: String)` produce one
overload, not two. A signature typed by the member's own generic parameters binds
exactly the ones it names — `@Injectable<Boxable> struct Box<X, Y>` with
`init(x: X, y: Y)` yields

```swift
@attached(peer, names: prefixed(_$zerk_injection_))
macro Injected<X, Y>(x: X, y: Y) = #externalMacro(module: "ZerkMacros", type: "InjectedMacro")
```

Each forwarding signature gets a `InjectedDynamically` twin alongside it, so both
attributes take the same arguments:

```swift
@attached(accessor)
macro InjectedDynamically(title: String) = #externalMacro(module: "ZerkMacros", type: "InjectedDynamicallyMacro")
```

Because these are module-local, every base form has to be restated too — Swift's
name lookup stops at the first scope declaring the name, so a module that gained
one argument-forwarding overload would otherwise lose plain `@Injected` and
`@Injected(\.member)` to shadowing.

## A plain key

```swift
protocol Logging {}

@Injectable<Logging>
struct Logger: Logging {
    init() {}
}
```

```swift
extension Zerk<Logging> {
    nonisolated static var logger: Logging {
        if let interjected = _$interjected(for: \.`logger`) {
            return interjected
        }
        return Logger()
    }

    nonisolated static func inject() -> Logging {
        logger
    }

}
```

Three things, and every generated member is some variation on them.

**The named member.** `logger` — the type's name, lower-camel-cased, because an
initializer states no name of its own. It returns the *key*, `Logging`, not the
concrete `Logger`. It is a `static var` rather than a `static func` because the
provider takes no parameters and has no effects; anything else forces the
function shape.

**The interjection guard.** Every member body opens with it. `_$interjected(for:)`
returns `Injectable?` concretely, which is why there is no type annotation on the
call, and it is `@inlinable` with the `#if DEBUG` inside — so a release build
deletes both the branch and the key-path formation. The key path names a point in
this key's [`Interjection` namespace](#the-interjection-namespace).

**`inject()`.** The single entry point every `@Injected` property, every resolved
dependency parameter and every `@injected` argument goes through. It delegates to
whichever member the resolver elected primary; the construction and the guard
live in that member, never here.

`nonisolated` is spelled out on every member. A provider that carries a global
actor gets `@MainActor` in the same position instead.

## A value

```swift
@InjectableValue
var apiBaseURL: String { "https://api.example.com" }

enum Config {
    @InjectableValue(.referenced)
    static var retryCount: Int = 3
}
```

```swift
extension Zerk<String> {
    nonisolated static var apiBaseURL: String {
        if let interjected = _$interjected(for: \.`apiBaseURL`) {
            return interjected
        }
        return "https://api.example.com"
    }
}

extension Zerk<Int> {
    nonisolated static var retryCount: Int {
        get {
            if let interjected = _$interjected(for: \.`retryCount`) {
                return interjected
            }
            return Config.retryCount
        }
        set {
            Config.retryCount = newValue
        }
    }
}
```

A value is reached by name, so it never gets an `inject()` — the extension holds
the member and stops. The two injection methods are visible in the bodies: the
copied value's body was *transplanted* into the accessor and the original
declaration is never read again, while the referenced one reads through
`Config.retryCount` on every access. Only a settable source earns a setter, and
only then does the member need an explicit accessor pair.

See [`@InjectableValue`](../Macros%20and%20Markers/InjectableValue.md) for which
method to pick.

## A singleton

```swift
protocol Caching {}

@Singleton
@Injectable<Caching>
final class MemoryCache: Caching {
    init() {}
}
```

```swift
private enum _$zerk_singletons {
    nonisolated(unsafe) static let memoryCache: MemoryCache = MemoryCache()
}

extension Zerk<Caching> {
    nonisolated static var memoryCache: Caching {
        if let interjected = _$interjected(for: \.`memoryCache`) {
            return interjected
        }
        return _$zerk_singletons.memoryCache
    }

    nonisolated static func inject() -> Caching {
        memoryCache
    }

}
```

The shared instance lives in a file-private `enum`, one `static let` per
singleton **type** — not per key. `Zerk<A>` and `Zerk<B>` are distinct generic
specializations with distinct static storage, so storing the instance on them
directly would give a type injectable under two keys two instances, and
"singleton" would only hold within a key. The storage member is the type's name,
lower-camel-cased; two singletons that would claim the same storage name are a
build error rather than a collision in generated code.

`nonisolated(unsafe)` acknowledges that sharing the instance across isolation
domains is the documented contract of `@Singleton` — `static let` initialization
is already thread-safe in the runtime. A `@MainActor` singleton gets
`@MainActor static let` instead and needs no escape hatch, and neither does one
whose declaration says `Sendable`: there the compiler knows already, and warns
that the annotation is unnecessary.

The guard sits in the key's member, not in the storage initializer — it cannot be
in the initializer, since the guard is per key while the storage is per type.
That is also the better semantics: a double installed after the first resolution
still takes effect, and interjecting a singleton never builds the real instance
at all.

Where a singleton is reached from another isolation domain, the file also gets a
constraint check, so the `Sendable` failure lands on a line carrying an
explanation:

```swift
private func _$zerk_sendable_conformance_check<T: Sendable>(_: T.Type) {}

private func _$zerk_sendable_conformance_check_Clock_in_Screen() {
    // '@Singleton Clock' is injected into 'Screen'.
    // A shared instance that crosses isolation domains must be Sendable.
    _$zerk_sendable_conformance_check(Clock.self)
}
```

## A scoped instance

```swift
protocol Caching {}

extension InjectionScope {
    nonisolated static let session = InjectionScope("session")
}

@Scoped(.session)
@Injectable<Caching>
final class SessionCache: Caching {
    init() {}
}
```

```swift
// A scope named from a nonisolated slot must itself be nonisolated. Under
// SWIFT_DEFAULT_ACTOR_ISOLATION, write `nonisolated static let session = …`.
private enum _$zerk_scoped {
    nonisolated static let sessionCache = ZerkScopedBox<SessionCache>(scope: .session)
}

extension Zerk<Caching> {
    nonisolated static var sessionCache: Caching {
        if let interjected = _$interjected(for: \.`sessionCache`) {
            return interjected
        }
        return _$zerk_scoped.sessionCache.value { SessionCache() }
    }

    nonisolated static func inject() -> Caching {
        sessionCache
    }

}
```

The same shape as a singleton — one entry per **type**, read through a per-key
getter, with the interjection guard ahead of it — and for the same reasons. Two
things differ.

**The construction closure is at the member**, not in the storage. The box holds
no way to build its value, which is what keeps it `nonisolated` even for a
`@MainActor` type (the closure runs in the member's domain, not the box's) and
what keeps `Zerk.reset(_:)` synchronous and callable from anywhere.

**The slot is pinned to the member's isolation** rather than marked
`nonisolated(unsafe)`. `ZerkScopedBox` is already `Sendable`, so the escape hatch
is unnecessary and the compiler says so — but an unannotated slot would inherit
`SWIFT_DEFAULT_ACTOR_ISOLATION` and go out of reach of a nonisolated member.

A scoped instance crossing an isolation domain gets the same `Sendable` check a
singleton does, with `@Scoped` named in the comment.

## A parametric provider

```swift
protocol Storing {}

@Injectable<Storing>
struct DiskStore: Storing {
    init() {}
}

@Injectable
struct Report {
    let store: any Storing
    let title: String
    init(store: any Storing, title: String) { ... }
}

@Injectable
struct Dashboard {
    let report: Report
    init(report: Report) { ... }
}
```

```swift
extension Zerk<Report> {
    nonisolated static func report(store: any Storing = Zerk<any Storing>.inject(), title: String) -> Report {
        if let interjected = _$interjected(for: \.`report`) {
            return interjected
        }
        return Report(store: store, title: title)
    }

    nonisolated static func inject(title: String) -> Report {
        report(store: Zerk<any Storing>.inject(), title: title)
    }

}
```

Two different treatments of the same parameter list. The **named member** keeps
every parameter and gives each resolvable one a default — `store` defaults to its
own `inject()`, `title` has nothing to default to and stays required. So
`Zerk<Report>.report(title: "Q4")` works and `Zerk<Report>.report(store: mock, title: "Q4")`
also works: a default is an offer, not a decision.

`inject()` is the flattened form. It resolves everything it can, inline, and its
signature carries only what nobody could supply — here `title` alone. That is
what "bubbling" means, and it is transitive:

```swift
extension Zerk<Dashboard> {
    nonisolated static func dashboard(report: Report) -> Dashboard {
        if let interjected = _$interjected(for: \.`dashboard`) {
            return interjected
        }
        return Dashboard(report: report)
    }

    nonisolated static func inject(title: String) -> Dashboard {
        dashboard(report: Zerk<Report>.inject(title: title))
    }

}
```

`Dashboard` never mentions a title. Its `inject()` grew one because the subtree
below it needs one, and the argument is threaded down to `Zerk<Report>.inject`.
Note that `dashboard`'s own `report` parameter got **no** default: `Report` is
not resolvable without an argument, so there is no expression to default it to.

## A provider that splits

When a dependency cannot be reached from a default expression — because
resolving it is `async` or `throws`, or because it lives in another isolation
domain and the hop costs `await` — the member splits in two.

```swift
protocol Connecting {}

@Injectable<Connecting>
final class DatabaseConnection: Connecting {
    @InjectableProviding
    static func connect() async throws -> Connecting { DatabaseConnection() }

    init() {}
}

@Injectable
struct SyncEngine {
    let connection: any Connecting
    init(connection: any Connecting) { ... }
}
```

```swift
extension Zerk<SyncEngine> {
    nonisolated static func syncEngine(connection: any Connecting) -> SyncEngine {
        if let interjected = _$interjected(for: \.`syncEngine`) {
            return interjected
        }
        return SyncEngine(connection: connection)
    }

    nonisolated static func syncEngine() async throws -> SyncEngine {
        syncEngine(connection: try await Zerk<any Connecting>.inject())
    }

    nonisolated static func inject() async throws -> SyncEngine {
        try await syncEngine()
    }

}
```

The **explicit** variant takes the unreachable dependencies as required
parameters. It carries the interjection guard and the construction, so there is
exactly one of each per provider, and it stays synchronous — the effects belong
to the resolution, not to the building.

The **resolving** variant omits those parameters, resolves them in its body, and
delegates. It inherits the merged effects: `connect()` is `async throws`, so this
is too. The two arities always differ, because the explicit variant's extra
parameters are required, so the overload is never ambiguous.

Effects propagate outwards from here. `Zerk<Connecting>.inject()` is
`async throws` because its provider is; `Zerk<SyncEngine>.inject()` is
`async throws` because its dependency's is. This is also the point at which
[`@Injected`](../Macros%20and%20Markers/Injected.md) gives up — it expands to a
synchronous, non-throwing accessor, so a chain like this is reported as a build
error naming `try await Zerk<SyncEngine>.inject()` as the way out. See
[Concurrency](../Features/Concurrency.md).

## The companion `static var`

```swift
@Injectable
struct UserService {
    let logger: any Logging
    init(logger: any Logging) { ... }
}
```

```swift
extension Zerk<UserService> {
    nonisolated static func userService(logger: any Logging = Zerk<any Logging>.inject()) -> UserService {
        if let interjected = _$interjected(for: \.`userService`) {
            return interjected
        }
        return UserService(logger: logger)
    }

    nonisolated static var userService: UserService {
        userService()
    }

    nonisolated static func inject() -> UserService {
        userService()
    }

}
```

The `var` exists for reach, not for convenience: `@Injected(\.userService)` takes
a key path, and a key path can name a property but not a method. It only
delegates — the function keeps the construction, the guard and the interjection
point, so there is still one of each.

The pair is legal because `userService` and `userService(logger:)` are different
names, where `userService` and `userService()` would be a redeclaration. It is
emitted only where such a property is expressible:

- **parameters, all resolvable** — with none the member is already a `var`, and
  with an unresolvable one there is nothing to default it to. This is why
  `report(store:title:)` above has no companion.
- **no effects, its own or its dependencies'** — Swift refuses to form a key path
  to an `async` or `throws` property, and for an argument-free effectful member
  the two names would collide.
- **a member name used once for the key**, and not a generic member — a property
  takes no generic parameters.

## A generic key

```swift
@Injectable
struct Logger {
    @InjectableProviding
    init() {}
}

@Injectable
struct Cache<Element> {
    @InjectableProviding
    init(logger: Logger) {}
}
```

```swift
extension Zerk {
    nonisolated static func cache<Element>(logger: Logger = Zerk<Logger>.inject()) -> Cache<Element> where Injectable == Cache<Element> {
        if let interjected = _$interjected(for: \.`cache`) {
            return interjected
        }
        return Cache(logger: logger)
    }

    nonisolated static func inject<Element>() -> Cache<Element> where Injectable == Cache<Element> {
        cache()
    }

}
```

The extension header is **unconstrained**. It has to be: `extension Zerk<Cache<Element>>`
has no `Element` to name. Each member introduces the parameters itself and binds
the key in a `where` clause. The constraints written on the type are not
reproduced — the same-type requirement re-derives them, and a specialization that
violates one still fails at the call site with the constraint's own message.

A generic key's members are always functions, even argument-free ones: a property
takes no generic parameters, so the `Zerk<Cache<String>>.cache` spelling a
concrete key gets is not available here.

The same problem hits the interjection points, and is answered with a marker
protocol:

```swift
protocol `_$ZerkInjectable_Cache` {}
extension Cache: `_$ZerkInjectable_Cache` {}

extension Zerk.Interjection where Injectable: `_$ZerkInjectable_Cache` {
    nonisolated var `cache`: Void {}
}
```

`extension Zerk<Cache<Element>>.Interjection` would be "cannot find type 'Element'
in scope". A marker protocol conformed to by the base type scopes the point to
exactly that type's specializations instead, so the guard in the member is
unchanged. The type's name goes into the protocol name verbatim, inside a raw
identifier, so `Outer.Bar` and `OuterBar` cannot collapse onto one marker and
leak points between two families.

One key shape gets neither: a **parameterized existential**. An existential
conforms to nothing, so there is no marker to constrain by, and such a member
falls back to the by-key lookup, `if let interjected = _$interjected()` with no
point at all. Providers for such a key also carry an availability line, since
parameterized existentials are iOS 16 / macOS 13 and up and the plugin cannot
read the target's deployment version. See [Generics](../Features/Generics.md).

## The `Interjection` namespace

Each key's points are gathered at the end of the file, one `Void` property per
generated member:

```swift
extension Zerk<Loader>.Interjection {
    var `loader(store: Disk)`: Void {}
    var `loader(store: Memory)`: Void {}
}

extension Zerk<Reader>.Interjection {
    var `reader(disk:)`: Void {}
    var `reader(memory:)`: Void {}
}
```

They are kept off `Zerk<Key>` itself because hung there the point for an
argument-free member would collide with the member — both would be
`static var logger`. In the namespace every member gets one whatever its shape,
and `Zerk<Key>`'s own surface is untouched. The type is `Void` rather than
`Never` because a getter returning `Never` must call another never-returning
function, so `var loader: Never {}` does not compile. Names are raw identifiers
(SE-0451), which is what lets a point be spelled exactly like the member's
signature.

Naming escalates only as far as the key forces, and a group of same-named members
escalates as a whole:

| members sharing the name | point |
|---|---|
| one | `` `logger` `` |
| several, distinct labels | `` `reader(disk:)` `` |
| several, same labels | `` `loader(store: Disk)` `` |

The fixture above is two types with two initializers each: `Reader`'s are told
apart by their labels, `Loader`'s are not, so only `Loader` escalates to full
parameter types. Adding an overload can therefore rename an existing point, which
turns interjections naming it into compile errors — the intended outcome, since
the name really did stop identifying one member. See
[Interjection](../Testing/Interjection.md).

## An `@injected` parameter overload

```swift
final class AuditTrail {
    init(@injected logger: Logger, label: String) {}
}

struct Exporter {
    func export(@injected logger: Logger, to path: String) -> Int { 0 }
}
```

```swift
extension AuditTrail {
    nonisolated convenience init(label: String) {
        self.init(logger: Zerk<Logger>.inject(), label: label)
    }
}

extension Exporter {
    nonisolated func export(to path: String) -> Int {
        export(logger: Zerk<Logger>.inject(), to: path)
    }
}
```

The overload omits the marked parameters and fills them from the graph;
everything unmarked passes through unchanged, labels included. The original
declaration is untouched, so both forms remain callable — passing a double
explicitly is just calling the one you wrote.

An initializer on a `class` becomes a `convenience init`, which is the only legal
shape for one initializer delegating to another there; on a `struct` or `enum` it
is a plain `init`. Effects merge in the same way they do for a provider: an
`async` resolution makes the overload `async`, and a dependency in another
isolation domain merges in as `async` too. Requirements the resolution cannot
satisfy bubble onto the overload, after the member's own parameters. See
[Parameter markers](../Macros%20and%20Markers/ParameterMarkers.md).

## The thunk for a global `@Injectable`

```swift
struct Session {}

@Injectable
var urlSession: Session { .init() }
```

```swift
nonisolated private func _$zerk_provider_urlSession() -> Session { urlSession }

extension Zerk<Session> {
    nonisolated static var urlSession: Session {
        if let interjected = _$interjected(for: \.`urlSession`) {
            return interjected
        }
        return _$zerk_provider_urlSession()
    }

    nonisolated static func inject() -> Session {
        urlSession
    }

}
```

Inside `extension Zerk<Session>` the unqualified name `urlSession` resolves to
the member being defined, so reading the global directly would be infinite
recursion — the compiler only warns, "attempting to access within its own
getter". A forwarding function declared at *file scope* breaks the cycle, because
file scope has no `Self` for the name to bind to.

Only a **global** declaration needs one. A static member is reached by its
qualified path — `Container.urlSession` — and gets no thunk. The thunk carries
the declaration's isolation and effects, and a generic one carries its parameters
and its generic clause. From `@Injectable func makeBox<X, Y>(x: X, y: Y) -> Box<X, Y>`:

```swift
nonisolated private func _$zerk_provider_makeBox<X, Y>(x: X, y: Y) -> Box<X, Y> { makeBox(x: x, y: y) }
```

Top-level values solve the same problem the same way: a referenced one gets
`_$zerk_ref_<name>()`, plus `_$zerk_set_<name>(_:)` when it is settable.

```swift
nonisolated private func _$zerk_ref_baseURL() -> String { baseURL }
```

## Emission order

The file is assembled in a fixed order, and everything within each part is
sorted:

1. Header comment, `import Zerk`, then the modules the read files imported.
2. The `macro Injected` declarations.
3. `extension Zerk<Key>` for each injectable value, by value name.
4. File-scope thunks — value references and global `@Injectable` declarations.
5. `private enum _$zerk_singletons`, then `private enum _$zerk_scoped`, if the
   module declares any of either.
6. `extension Zerk<Key>` per key, keys sorted; within a key, members by name,
   then `inject()`.
7. `extension <Type>` per type with `@injected` members, types sorted.
8. Marker protocols and their conformances, then every `Interjection` namespace.
9. The `Sendable` constraint checks.

Parts 3 through 9 are omitted entirely when a module contributes nothing to them.
A target with no Swift sources gets no codegen command at all, rather than a
command that would write an empty file.
