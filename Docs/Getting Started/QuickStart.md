# Quick start

The smallest complete graph: a value, an injectable keyed by a protocol, and a consumer that resolves it. This page shows the three declarations and then the code the plugin actually generates for them.

## The three parts

```swift
import Zerk

// 1. A value the graph can use to satisfy parameters of matching type
@InjectableValue
var baseURL: String {
    "https://api.example.com"
}

// 2. An injectable keyed by a protocol
protocol ApiServicing: AnyObject {
    var host: String { get }
}

@Singleton
@Injectable<ApiServicing>
final class ApiService: ApiServicing {
    let host: String

    @InjectableProviding
    init(baseURL: String) {       // `baseURL: String` auto-satisfied by the value above
        self.host = baseURL
    }
}

// 3. A consumer
struct FeedViewModel {
    @Injected
    var apiService: ApiServicing   // resolved at init, at compile-time-verified call site
}
```

Nothing here registers anything at runtime. `@Injectable<ApiServicing>` says the key is the protocol rather than the class; `@InjectableProviding` says which initializer Zerk may call; `@InjectableValue` puts `baseURL` in the graph so the provider's `baseURL: String` parameter has something to be filled from. Values are matched by key **and** name together, which is what stops two unrelated `String` values from being interchangeable.

## What the plugin generates

Run the codegen over exactly that source and this is the whole output file — nothing trimmed, nothing paraphrased:

```swift
// Generated by Zerk
// Do not change by hand.

import Zerk

@attached(peer, names: prefixed(_$zerk_injection_))
macro Injected() = #externalMacro(module: "ZerkMacros", type: "InjectedMacro")

@attached(peer, names: prefixed(_$zerk_injection_))
macro Injected<T>() = #externalMacro(module: "ZerkMacros", type: "InjectedMacro")

@attached(peer, names: prefixed(_$zerk_injection_))
macro Injected<T>(_ keyPath: KeyPath<Zerk<T>.Type, T>) = #externalMacro(module: "ZerkMacros", type: "InjectedMacro")

extension Zerk<String> {
    nonisolated static var baseURL: String {
        if let interjected = _$interjected(for: \.`baseURL`) {
            return interjected
        }
        return "https://api.example.com"
    }
}

private enum _$zerk_singletons {
    nonisolated(unsafe) static let apiService: ApiService = ApiService(baseURL: Zerk<String>.baseURL)
}

extension Zerk<ApiServicing> {
    nonisolated static var apiService: ApiServicing {
        if let interjected = _$interjected(for: \.`apiService`) {
            return interjected
        }
        return _$zerk_singletons.apiService
    }

    nonisolated static func inject() -> ApiServicing {
        apiService
    }

}

extension Zerk<ApiServicing>.Interjection {
    var `apiService`: Void {}
}

extension Zerk<String>.Interjection {
    var `baseURL`: Void {}
}
```

Reading it in order:

**The value becomes a member.** `Zerk<String>.baseURL` reproduces the declaration's body. It is named, not anonymous, because a value is matched by key and name — a second `String` value would sit beside it rather than compete with it.

**`@Singleton` gets private storage.** `_$zerk_singletons` is a `private enum` in the generated file, one `static let` per singleton, each initialized by calling the provider with its dependencies already resolved — here `Zerk<String>.baseURL`, wired in at build time because the provider's parameter matched a value in the graph. Swift's lazy static initialization is what makes it built once and on first use.

**The key gets a member and an `inject()`.** `Zerk<ApiServicing>.apiService` is the named member for this provider; `inject()` is the primary — the one thing that answers "give me an `ApiServicing`" without naming a provider. With one provider for the key they agree, and `@Injected` reaches the key through `inject()`.

**Every member gets an interjection point.** The first line of each member is where a test double stands in. `_$interjected(for:)` is `@inlinable` and returns `nil` outside `DEBUG`, so the branch and the key-path formation are deleted — it compiles to nothing in release. The points live in a `Zerk<Key>.Interjection` namespace and are named, via raw identifiers, verbatim after the member's signature, which is how `#Interject(\.apiService, with: MockApi())` names one.

**The `macro Injected` redeclarations** are the plugin restating `@Injected` inside the module it generates into, so it can add one overload per distinct `inject()` signature. They shadow the declarations in the `Zerk` library wherever the plugin runs.

`@Injected var apiService` expands to a stored property whose default value is `Zerk<ApiServicing>.inject()`. The namespace itself is an empty `public enum Zerk<Injectable> {}`; everything lives in the generated extensions.
